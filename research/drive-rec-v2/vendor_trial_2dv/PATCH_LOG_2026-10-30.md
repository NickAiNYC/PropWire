## Defect 1 — historical event discovery

**Owner finding**: `fetch_trial_quotes.py` discovered event IDs via
`GET /sports/{sport_key}/events` — a current-events endpoint, not a
reliable way to discover completed games from 2025 or earlier in 2026.

**Vendor facts** (docs retrieved 2026-10-30): completed games surface via
`GET /sports/{sport}/scores` only within `daysFrom<=3`; there is no
historical events-list endpoint. Event IDs for completed games must come
from recorded sources (captured while upcoming, owner records/exports,
vendor support).

**Fix**:
- Acquisition no longer calls any events endpoint. It requires a
  **verified event-ID mapping** (`event_id_map.json`): every entry carries
  `event_id`, `status`, `discovery_source`, `discovery_timestamp_utc`,
  `commence_time_verified`, `sport_key`.
- `fetch_trial_quotes.py --dry-run` refuses to run without the map
  (selftest T11); REAL mode likewise.
- The fetch gate: quote requests happen only for games whose map entry has
  non-null `event_id` and `status == "verified"`; all other games are
  ledgered as discovery misses and skipped (fail-closed per game, zero
  spend).
- The exact map used is copied byte-for-byte into the run directory and
  hash-listed in the manifest; V3 verifies provenance fields (source and
  timestamp present and valid, commence within the schedule window,
  response event ids trace to the map).
- New Stage-A tool `discover_event_ids.py`: builds a candidate map from
  owner-supplied candidate IDs (verified via event detail against the
  precommitted schedule, ~1 modeled credit each), owner attestation
  (recorded as such), or explicitly-labeled probes; every entry records
  discovery source + timestamp; metered with the same Meter.
- `artifacts/event_id_map.json` ships as an UNVERIFIED template for the 8
  precommitted games (the 2025-season IDs still need to be sourced —
  owner records, vendor support, or attestation).
- Go-forward strategy (recorded in `trial_config.json`): capture event IDs
  from `/events` while games are upcoming and archive them — the reliable
  historical mapping pattern for the full acquisition.

## Defect 2 — credit guard does not measure real spending

**Owner finding**: in REAL mode `before_rem` was initialized to `None`, so
`actual_credits`, cumulative spending, and the 600-credit cap could never
be computed from real balances; there was no budget check around discovery
requests or HTTP retries.

**Fix** (`credit_meter.Meter`, used by both fetcher and discovery tool):
- **R1** actual consumption per response = `x-requests-used` delta (the
  vendor's cumulative counter — immune to prior usage on the key), with a
  zero-cost baseline established first by two `GET /v4/sports` calls
  (docs: unmetered; second call's delta verifies the first was free).
- **R2** cross-checked against `x-requests-last` (per-call self-report)
  and the `x-requests-remaining` delta; disagreement raises
  `ConsumptionUnestablished`.
- **R3** a response missing `x-requests-used` on a non-retryable status
  raises `ConsumptionUnestablished` → run aborts PARTIAL; the response
  body is still persisted (evidence) and the abort reason is recorded in
  the manifest and audited by V9.
- **R4** pre-flight authorization: measured spend + modeled cost of the
  NEXT request must stay within `credit_budget_cap`; **every retry attempt
  and every discovery/baseline request is authorized and metered**.
- **R5** post-observation: measured cumulative spend re-checked against
  the cap.
- **R6** one ledger row per response (attempt-level), with used/remaining
  before+after, per-call cost, cumulative totals; `ledger_summary()`
  recomputes everything from the recorded readings for V9.
- V9 rewritten: FAILs on unestablished rows, header inconsistencies,
  null actuals outside tolerated open/baseline rows, measured total
  (all kinds) over cap, quote actual-vs-modeled mismatches, and runs that
  aborted on consumption failures.
- Dry-run now exercises the SAME metering path (the fixture server
  simulates usage headers), so the harness genuinely tests the REAL code.

# 2026-10-31 — Owner-ordered patch (pre-acquisition): market-key correction

**Authorization**: two owner orders, both 2026-10-31. Order 1 — "Land

**Finding** (pre-acquisition vendor-doc verification, 2026-10-31; owner
instruction: "confirm the exact receiving-yards market key"):

- `trial_config.json` (`market_candidates`) and `make_fixtures.py`
  (`MARKET_KEY`) carried `player_receiving_yards` — a string that appears
  **nowhere** in the vendor's official betting-markets catalogue.
- Vendor's NFL Player Props table (retrieved 2026-10-31,
  the-odds-api.com/sports-odds-data/betting-markets.html): the
  receiving-yards Over/Under market key is **`player_reception_yds`**
  (alternate line: `player_reception_yds_alternate`). Cross-confirmed via
  the `oddsapiR` package documentation (an independent wrapper of the API).
- **Impact if unfixed**: every historical event-odds request would cost its
  10 credits but return no market matching the requested key → V4 (minimum
  players per game) and V5 (quote parsing) fail across the board; worst case
  the trial's entire 240-credit quote budget burned for **zero quotes**
  (8 games × 3 timestamps × 10 credits). Caught pre-acquisition — zero
  credits consumed to date.
- Sanctioned by the repo's own protocol: the README execution-prerequisite
  step 0 already instructed "confirm the exact market key … edit
  `trial_config.json` `market_candidates` if it differs (do this BEFORE the
  run; it is a config fix, not a protocol change)", and PRECOMMITMENT.md P2
  pre-declared the market key as a candidate "resolved empirically at first
  request … any change is recorded in the run manifest" — correcting the
  candidate **before** the first request is strictly better than resolving
  it empirically by burning a paid request.

**Fix (three code locations, two orders)**:

1. `trial_config.json`: `market_candidates`
   `player_receiving_yards` → `player_reception_yds` (order 1; exactly the
   staged patch `proposed_2dv_market_key_fix.patch`).
2. `make_fixtures.py`: `MARKET_KEY` `player_receiving_yards` →
   `player_reception_yds` (order 1). Fixtures regenerated: the 48 response
   files (24 clean + 24 faulted) changed **only** in the market-key line
   (142 key lines in total; the complete diff contains no other change); the
   6 non-response fixture files (`event_id_map.json`,
   `sample_manifest.json`, `sports_list.json` × clean/faulted) are
   byte-identical to the previous commit; regeneration is proven
   byte-identical on repeat runs (selftest T1).
3. `verify_v1_v10.py`: the V1/V6 market matcher extended at both sites
   (V1 ~line 185, V6 ~line 472; order 2) —
   `mkey = m.get("key") or ""; if "receiving" in mkey or "reception_yds" in mkey:`
   (staged patch `proposed_2dv_verifier_market_match.patch`). Matching
   semantics unchanged: still a market-family match covering the main and
   alternate lines, now consistent with the vendor's verified vocabulary.
